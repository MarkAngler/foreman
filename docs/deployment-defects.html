FOR-001
Deployed FastAPI rejects every dependency-injection annotation
Blocker Open
Discovered2026-05-17 — by direct httpx probe with Databricks workspace OAuth Bearer
AffectsEvery FastAPI route in foreman-dev (deployed Databricks App)
Affects codesrc/foreman/lib/tracing.py:32; every @trace-decorated handler in src/foreman/app/routers/
Owner(unassigned)
Target fix(none set)

Symptom

Every route returns 422 with payloads mis-classifying handler parameters as required query parameters:

$ POST /workspaces/list  (Databricks-OAuth Bearer)
422 {"detail":[
  {"type":"missing","loc":["query","scope"], "msg":"Field required","input":null},
  {"type":"missing","loc":["query","params"],"msg":"Field required","input":null}
]}

POST /workspaces additionally reports response and body as missing query params. POST /workspaces/{ws}/peers/list returns 500.

Root cause (suspected)

trace = mlflow.trace in tracing.py:32 is re-exported and applied to every FastAPI handler (≈50 sites across routers/). FastAPI uses inspect.signature() to introspect dependency annotations. Locally mlflow 3.12.0 preserves signatures and tests pass; on the deployed runtime, mlflow resolves to a version whose @trace wrapper strips Annotated[..., Depends()] info, so FastAPI falls back to treating every parameter as a required query param.

Evidence

  • Local inspect.signature(list_workspaces) shows the full Annotated[..., Depends(...)] annotations.
  • Local in-process E2E (28 / 28 assertions) succeeds with the same code through httpx.ASGITransport.
  • Local unit suite (220 / 220) passes.
  • Deployed /healthz and / work (handlers without Depends deps).
  • Deployed /openapi.json returns 500 (consistent with broken introspection — see FOR-005).

Recommended fix

  1. Pin mlflow in requirements.txt to the local-known-good version (currently mlflow==3.12.0), then redeploy.
  2. If pinning isn't sufficient, move tracing off FastAPI handlers and apply @trace one layer down (service / repository functions) so signature introspection isn't disturbed.
  3. Long-term: wrap with functools.wraps(..., assigned=("__wrapped__","__signature__","__annotations__",...)) to guarantee survival regardless of mlflow version.

FOR-002
MCP client cannot traverse Databricks Apps OAuth proxy
Blocker Open
Discovered2026-05-17 — first foreman_list_workspaces call
AffectsAll 10 foreman MCP tools when calling the deployed app
Affects codesrc/foreman/mcp/client.py:36, src/foreman/mcp/auth.py:117-123
Owner(unassigned)

Symptom

Every request from ForemanClient to the deployed app returns HTTP 302 to the Databricks workspace OIDC login URL. The foreman HS256 JWT never reaches the FastAPI process.

HTTP/1.1 302 Found
location: https://adb-…/oidc/oauth2/v2.0/authorize?…&redirect_uri=…/.auth/callback&…
content-length: 0

Root cause

Databricks Apps' OAuth proxy gatekeeps every request. ForemanClient._headers() in client.py:36 sends only Authorization: Bearer <foreman_HS256_JWT>. The proxy doesn't recognize this token and redirects before forwarding. The entire foreman JWT system in lib/auth.py is therefore unreachable from outside the workspace.

Recommended fix

Pick one of:

  • (a) Trust Databricks OAuth identity: drop the foreman HS256 JWT layer entirely; have current_scope derive identity from the proxy's injected headers (X-Forwarded-User, X-Forwarded-Email, etc.) and re-derive scope from per-workspace ACL tables.
  • (b) Dual-header scheme: client sends both a Databricks OAuth Bearer (for the proxy) and the foreman JWT in X-Foreman-Token; a new FastAPI dependency reads the custom header first, falling back to Authorization for in-process testing.
  • (c) Disable Apps OAuth: if the app is intended for trusted machine-to-machine use, configure the App to not require user authorization (Databricks docs: Apps user authorization) and keep the foreman JWT as sole auth.

Recommendation: option (b) — preserves the existing foreman scope/JWT design while satisfying the Apps proxy contract.

FOR-003
ForemanClient silently swallows 3xx redirects, returning None
Blocker Open
Discovered2026-05-17 — explains why foreman_list_workspaces "succeeded" with payload null
AffectsEvery ForemanClient method that uses _request (all REST tools; not chat)
Affects codesrc/foreman/mcp/client.py:48-54, 209-215
Owner(unassigned)

Symptom

Any 3xx response with an empty body (typical for OAuth-proxy redirects) is treated as a successful no-content reply. Callers receive None with no error, indicator, or log.

async def _request(self, method, path, **kwargs):
    async with self._client() as c:
        resp = await c.request(method, path, headers=self._headers(), **kwargs)
    _raise_for_status(resp)                       # only fires on >=400
    if resp.status_code == 204 or not resp.content:
        return None                               # 302 with empty body → None
    return resp.json()

This bug masked FOR-002 completely during the first probe; the tool "appeared to succeed" with payload null.

Recommended fix

  • Set follow_redirects=True on the httpx.AsyncClient in client.py:41-46, or
  • Explicitly raise on any 3xx in _raise_for_status, including the Location header in the error message so the redirect target is visible.

Verification

  • Add a unit test: respx mocks a 302; expect RuntimeError containing the Location URL.
  • Live: with FOR-002 still open, an MCP tool call now surfaces the OIDC redirect URL instead of returning None.
