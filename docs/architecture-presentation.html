foreman

A clean-room rebuild of honcho.dev — an identity & memory layer for AI agents — on Databricks.

Architecture · data flow · component-by-component

Lakebase Postgres Vector Search Delta / UC FastAPI on Apps Lakeflow Jobs

What foreman is

  • Identity layer — workspaces, peers (humans or agents), sessions, messages.
  • Memory layer — raw conversation recall + derived facts about peers (what they said, what we inferred).
  • Dialectic agent — a tool-calling chat loop that reasons over that memory.
  • Distributed as a Databricks Asset Bundle — one bundle deploy installs the entire footprint.

Mental model: a brain with three storage organs and a few specialized workers.

Three storage layers, one role each

Lakebase Ledger

Postgres. The system of record. ACID, ordered reads, composite PKs, partial unique indexes.

11 tables: workspaces, peers, sessions, session_peers, messages, documents, queue_items, active_queue_session, webhook_endpoints, peer_cards, workspace_llm_config (+ documents_mirror view).

Vector Search Recall

Semantic memory. ANN reads in milliseconds.

messages_idx — Direct Access, written inline by the app (<1s freshness).

documents_idx — Delta Sync with managed embeddings, sourced from documents_delta.

Delta / UC Derived

Batch-processed insights — written by Spark jobs only.

documents_delta, session_summaries_delta, webhook_results_delta, deriver_state, summarizer_state_delta.

Key rule: Lakebase is the only truth. Delta and Vector Search are downstream views — rebuildable from Lakebase + messages, never the other way around.

Flow A — write path (message arrives)

POST /workspaces/{w}/sessions/{s}/messages

client ──► FastAPI │ ├─ 1 ─► Lakebase.messages INSERT (durable truth) │ ├─ 2 ─► embed(content) Foundation Model API, 1024-dim │ └─ 3 ─► messages_idx.upsert Direct Access, inline ◄── 201 returned only after all three succeed

Synchronous so a "send-then-immediately-query-memory" flow has <1s freshness — the app does the embed and upsert itself rather than waiting for a background pipeline.

Concurrently, four jobs are processing the new row asynchronously — see Flow C.

Flow B — read path (querying memory)

query ──► Vector Search ├─ query_messages() → messages_idx raw conversation recall └─ query_documents() → documents_idx derived-facts recall
  • The dialectic agent and query endpoints never read Lakebase for memory — memory lives in Vector Search.
  • Lakebase is read only for CRUD metadata (list workspaces, get peer config, resolve LLM endpoint) and by jobs for watermarked tailing.

The asymmetry is the whole design: synchronous freshness path via Direct Access VS, asynchronous derivation path via Delta + Delta Sync VS.

Flow C — background derivation

Four Lakeflow Jobs, all Spark + sync, all read Lakebase via JDBC and write Delta:

deriver every 1 min

Pull new messages by watermark → LLM extracts explicit facts → MERGE documents_delta → trigger documents_idx sync.

summarizer every 5 min

For sessions past an N-new-message threshold, LLM produces a rolling summary; APPEND session_summaries_delta.

dreamer hourly

Surprisal-prioritized deduction → induction passes over explicit facts. Writes deductive/inductive documents with source_ids DAG; refreshes peer_cards.

webhooks every 1 min

Drain queue_items where task_type='webhook' → POST with HMAC signature → APPEND webhook_results_delta.

documents_delta — the derived-knowledge ledger

deriver job (every 1 min) │ MERGE (sha256 PK ⇒ idempotent) ▼ ┌─────────────────┐ │ documents_delta │ ◄── source of truth for derived facts │ (UC Delta) │ CDF enabled └────────┬────────┘ │ ┌────────────┴────────────┐ ▼ ▼ Delta Sync (managed Lakeflow Synced Table embeddings) (reverse ETL) │ │ ▼ ▼ ┌──────────────┐ ┌──────────────────┐ │ documents_idx│ │ documents_mirror │ │ (VS) │ │ (Lakebase) │ └──────────────┘ └──────────────────┘ ▲ ▲ │ ANN query │ transactional FK joins │ from app │ from app

Delta is mandatory upstream because the Delta Sync VS index requires a UC Delta source with Change Data Feed — you cannot point Delta Sync at Postgres.

Observer / observed — the perspective model

Honcho's mental model: every peer maintains their own private picture of every other peer, including themselves. A fact is never bare — it is always "observer X believes Y about observed Z".

In a session with Alice, Bob, Carol — Alice sends "I'm vegetarian" → deriver writes three rows:

observerobservedcontentmeaning
AliceAliceis vegetarianAlice's self-knowledge
BobAliceis vegetarianwhat Bob now knows about Alice
CarolAliceis vegetarianwhat Carol now knows about Alice

Query with observer='Bob' AND observed='Alice' to answer "what does Bob know about Alice?". Privacy and perspective fall out naturally.

Inside the deriver job

  1. Read watermark — deriver_state Delta KV table stores last_processed_message_id.
  2. Pull batch from Lakebase via JDBC: SELECT … FROM messages WHERE id > {watermark} ORDER BY id LIMIT 5000.
  3. Resolve observers per (workspace, session) from session_peers where left_at IS NULL.
  4. Group + call LLM per (workspace, session, observed=sender) via llm_dispatch.chat_sync(role='deriver', …).
  5. Fan out each extracted fact across observers (N facts × M observers = N×M rows).
  6. Deterministic ID — sha256(workspace|observer|observed|content)[:24]. Same tuple → same ID → MERGE deduplicates for free.
  7. MERGE into documents_delta → trigger documents_idx sync (best-effort) → advance watermark.

Crash mid-batch is safe: next run reprocesses the same window, idempotent IDs make the MERGE a no-op.

Webhooks — outbound notifications

Pattern: "foreman, when X happens in my workspace, tell my system Y so it can do Z." Stripe-webhook-style HMAC-signed POSTs.

[ foreman event ] ──► queue_items (Lakebase) │ ▼ webhooks job (every 1 min) │ ▼ POST /your-url X-Foreman-Event: X-Foreman-Signature: sha256= body: {event_type, workspace_name, occurred_at, data} │ ▼ webhook_results_delta
  • 2xx → success · 408/429/5xx → retryable · other 4xx → permanent.
  • Retries bounded across runs (skip if ≥ 5 prior attempts in webhook_results_delta) — failing endpoints aren't hammered forever.
  • Spark can't write Lakebase here (spine rule) — a Phase-3 reconciler flips queue_items.processed back in Lakebase from webhook_results_delta.

The dialectic agent

A tool-calling chat loop that reasons over a peer's memory. Streams an SSE response with intermediate tool calls.

Tools the loop can call

  • search_memory — semantic query over documents_idx (derived facts).
  • search_messages — semantic query over messages_idx (raw conversation).
  • Peer-card / session-summary / observer-observed lookups, etc.

Tool-calling quirk

The Databricks SDK's serving_endpoints.query does not propagate a tools= param. llm_dispatch._invoke therefore routes any call with tools in kwargs through the OpenAI-compatible path against the same endpoint, regardless of the declared provider.

Practical: a workspace must have workspace_llm_config(role='dialectic', provider='openai-compatible', …) for the agent to function.

Per-workspace LLM configuration

Five overridable roles per workspace in workspace_llm_config:

dialectic · deriver · summarizer · dreamer · embeddings

Auth — HS256 JWT, hierarchical scopes

┌─────────────────────────────────────────────────────┐ │ admin │ every workspace, every action │ │ workspace │ one workspace, every action │ │ peer │ one peer in one workspace │ │ session │ message-create within one session │ └─────────────────────────────────────────────────────┘
  • Signing key lives in Databricks secret foreman/jwt_signing_key; loaded + cached at process start.
  • Claims: {ad?, w?, p?, s?, t, exp}.
  • The bootstrap admin JWT is generated at install time and stored as foreman/bootstrap_admin_token.
  • Use it against POST /workspaces/{w}/keys to issue scoped tokens for downstream consumers.

v1 constraint: no Lakebase RLS. Anyone with direct Lakebase access bypasses honcho ACLs — auth is enforced at the API boundary, matching honcho's design.

Install — one command, ~20 minutes

python install/install.py
  1. install/bootstrap.py — creates Lakebase instance (~5m), VS endpoint (~10m), secret scope, JWT signing key, bootstrap admin token.
  2. databricks bundle deploy — UC schema, FastAPI app, four background jobs.
  3. databricks bundle run schema_init — Alembic migrations against Lakebase, Delta tables, Lakebase ↔ Delta synced tables, both Vector Search indexes.
  4. databricks bundle run foreman_app — starts the FastAPI app.

Every resource is tagged project=foreman (jobs via resources/jobs.yml, Lakebase + VS endpoint via install/bootstrap.py) — the footprint is filterable in Account Usage / Billing.

MCP server — Claude Code integration

  • stdio MCP server in src/foreman/mcp/ exposes ~10 foreman tools to MCP clients (Claude Code, etc.).
  • Auth flows through databricks-sdk by default — OAuth U2M, PAT, or named profile.
  • FOREMAN_TOKEN and FOREMAN_BASE_URL env vars override for CI / scripted setups.
  • Each tool call ultimately hits the same FastAPI REST surface as any other client.

Net effect: an AI coding agent can directly inspect/modify a foreman deployment — list workspaces, query memory, post messages, issue tokens — without manually crafting HTTP calls.

Why derived facts live in Delta (not Lakebase, not VS directly)

  1. Spark writes Delta natively. JDBC-to-Postgres from a Spark cluster is serial and brittle; Delta is parallel + MERGE-friendly + transactional. Right tool for the writer.
  2. Delta Sync VS requires a Delta source. Managed embeddings can only read from a UC Delta table with Change Data Feed. You cannot point Delta Sync at Postgres.
  3. Lakebase shouldn't absorb batch write pressure. The OLTP path must stay responsive on message-create. Delta absorbs batch load on separate storage + compute. Workload isolation.
  4. Delta is a replayable derived ledger. Swap the embedding model? Re-sync from documents_delta. Want analytics on extraction rates? Cheap SQL warehouse query.

One-line answer: derived knowledge lives in Delta because that's where Spark wants to write, where Delta Sync VS needs to read, and where Lakebase doesn't want to be bothered.

Memory hooks — sentences to remember

  1. Lakebase is the ledger; everything else is a view of it. Messages land in Lakebase first, always.
  2. Two VS indexes, two write disciplines. messages_idx is hand-fed by the app for freshness; documents_idx is Databricks-managed from a Delta source because batch is fine.
  3. Delta is where Spark jobs put derived knowledge. It flows forward to documents_idx (app reads via VS) and reverse via synced tables to documents_mirror (transactional reads without JDBC-to-Delta).
  4. documents_delta is foreman's long-term memory store — perspective-tagged facts, content-addressed IDs, MERGE for free idempotency.
  5. The webhooks job is the only thing in foreman that talks to the outside world after the fact.

Synchronous freshness path through Direct Access VS · asynchronous derivation path through Delta + Delta Sync VS.
