foreman

Identity & memory for AI agents — when to use it, when to skip it

What foreman is

  • Per-user identity (peers) and conversation containers (sessions)
  • Long-term semantic memory over messages and derived facts
  • Background workers that turn messages into explicit, deductive, and inductive knowledge
  • Peer cards — evolving theory-of-mind for each peer about each other peer
  • A dialectic agent that answers "what does X think / know / want?" with tool-calling over the above

In one line: foreman adds continuity of relationship to an agent that would otherwise forget you between turns.

The decision

Reach for foreman when…

You expect the agent to recognize the same person across sessions, accumulate understanding of them, and act on that understanding. The relationship outlives any single conversation.

Skip foreman when…

The agent's job ends when the request ends. There is no "next time," no theory of the user, no benefit to remembering. Memory becomes latency, cost, and a privacy surface for no payoff.

In scope use foreman

Agents whose value compounds with knowing the user.

Personal coach / companion

fitness, journaling, language tutor, therapy adjunct

  • Same user, weeks-to-years of interaction
  • Goals, setbacks, preferences must persist between sessions
  • Dreamer turns scattered chats into stable inductions ("user gives up on cardio when traveling")
  • Peer cards let the agent open every session already knowing who it's talking to

Customer support with continuity

SaaS, fintech, insurance — any repeat-contact channel

  • The same customer opens five tickets over a year; an agent that re-asks "what plan are you on?" each time is a downgrade
  • Foreman gives the agent: prior-ticket recall, derived preferences, account-level theory-of-mind
  • Session-scoped JWTs map cleanly to ticket-scoped agent access
  • Webhooks let CRM stay in sync without polling

Multi-peer collaboration

group chats, advisory boards, agent-to-agent

  • foreman's first-class primitive: a session containing multiple peers (humans and/or agents)
  • Each peer holds a distinct model of every other peer — the dialectic agent answers "what does Alice think Bob believes?"
  • Fits negotiation copilots, deal rooms, multi-agent simulations, GTM war-rooms
  • Replacing this with a single shared context loses the per-perspective view that makes the product work

Sales / GTM copilots

account-based selling, CS, partnerships

  • One peer = one prospect or account; the agent's worldview about them is the moat
  • Deriver extracts explicit facts ("budget Q3", "champion: Priya") from call notes and email threads
  • Summarizer keeps a rolling state-of-the-account that fits in any prompt
  • Per-workspace LLM config — each tenant brings their own model + key

Research & longitudinal observability of users

product analytics with a soul, UXR copilots

  • You want to ask "what has this cohort started caring about over the last 90 days?"
  • Surprisal-prioritized dreamer surfaces the deltas, not just the volume
  • MLflow Tracing on every dialectic call gives auditability — important when conclusions about humans are involved

Out of scope skip foreman

Where foreman adds latency, cost, and complexity for no return — or actively gets in the way.

Stateless Q&A / FAQ bots

"what time does the store close?"

  • No user model needed — every visitor is interchangeable
  • Inline embedding on every message + dialectic tool-loops add hundreds of ms and dollars for zero recall benefit
  • A single LLM call with the FAQ in-context is the right answer
  • Peer cards never accumulate signal because there's no continuity to learn from

Single-turn tools

translators, summarizers, code formatters, classifiers

  • The unit of work is one input → one output; there is no "session" to be coherent across
  • foreman would turn a 200ms function into a multi-hop dance through Lakebase, Vector Search, and a tool-calling agent
  • If you find yourself creating a fresh peer per request, you're paying for a memory layer to immediately throw the memory away

Pure RAG over a static corpus

docs search, legal lookup, internal wiki Q&A

  • The knowledge lives in documents, not in evolving relationships with users
  • Use Vector Search directly — foreman's value-add (peers, peer cards, dialectic, dreamer) doesn't apply to static text
  • Adding foreman here means maintaining a Lakebase instance and four scheduled jobs to do nothing for you
  • Caveat: personalized RAG ("what would this user want from these docs?") does belong in foreman

Hard real-time / voice agents

sub-300ms turn-taking, IVR, live captioning

  • foreman's freshness guarantee is <1s, not <100ms — fine for chat, fatal for voice barge-in
  • The dialectic agent is a tool-calling loop; each hop costs a model call
  • For voice, keep memory in the LLM's session context and offload only between calls — possibly to foreman as a sidecar

One-shot / anonymous interactions

marketing chat widgets, kiosk concierges, demo bots

  • No stable identity → no peer → no memory worth keeping
  • The deriver and dreamer will dutifully spend tokens turning noise into "facts" about a peer who will never return
  • You end up with a Lakebase full of orphan peer cards and a bill to match

"It all fits in the context window"

short-lived agents, single-document copilots

  • If the entire relevant history fits comfortably in 200K tokens and you don't need cross-session recall, just pass the history
  • foreman shines when state must outlive the prompt — across sessions, across days, across agents
  • Don't introduce a database to solve a problem the model already solved for free

Strict consent / minimization regimes

regulated health data, minors, jurisdictions requiring explicit storage approval

  • The deriver and dreamer write inferred facts about users without per-fact consent
  • Peer cards are an evolving psychological profile — a feature in coaching, a liability under strict minimization rules
  • If every stored attribute needs a user-approved provenance trail, foreman's autonomous derivation is the wrong default
  • Mitigation exists (disable dreamer, restrict deriver to explicit-only), but at that point you're using ~30% of foreman

Throwaway batch pipelines

nightly classification of millions of records, LLM ETL

  • No peer, no session — the workload is rows, not relationships
  • Foreman's per-message embed-and-upsert is the wrong primitive for batch; use Spark + ai_query directly
  • If you find yourself disabling all four background jobs, you didn't need foreman

Heuristic

Use foreman if you can finish this sentence

"Next time this user comes back, the agent should already know ____ about them — and that knowledge should keep evolving."

Skip foreman if

The answer is "nothing" — or the user has no "next time."

foreman is a relationship system, not a memory bolt-on. The further your problem is from "an agent that knows people," the more foreman costs without paying back.
